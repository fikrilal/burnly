# Burnly Cost Calculator Engineering Proposal

## Status

Engineering proposal, based on analysis of the ccusage pricing pipeline
(20.0.19), the models.dev live API, and Burnly's existing cost provenance
model. Not an execution plan and does not approve implementation by itself.

## Context

Burnly surfaces cost for some sources but not others, and the coverage is
uneven:

- **Command Code** reports provider-computed `costUsd` per message.
- **Cline** reports its own cost metric from its local DB.
- **Claude Code, Codex, OpenCode, Pi** get cost from the bundled `ccusage`
  sidecar (`--offline --mode calculate`), which prices tokens with an
  embedded LiteLLM snapshot plus built-in tables.
- **Grok, Antigravity, ZCode** report no cost at all; their mappers always
  emit `UsageCost::Unavailable`.

Analysis of ccusage 20.0.19 and the models.dev API found:

- ccusage's embedded pricing snapshot covers Claude, OpenAI/GPT, ZAI/GLM,
  Azure, and (via a separate snapshot) Moonshot/Kimi well, but has **zero
  entries for DeepSeek, Mimo, Nemotron, Grok, Gemini, Qwen**.
- The live models.dev API has full pricing for those providers (e.g.
  `deepseek/deepseek-v4-flash` $0.14/$0.28, `mimo-v2.5` $0.14/$0.28, NVIDIA
  Nemotron-3-Ultra $0.75/$2.75 per 1M tokens) — the gap is ccusage's embedded
  snapshot, not the upstream data.
- Free-tier models (`deepseek-v4-flash-free`, `mimo-v2.5-free`,
  `nemotron-3-ultra-free`) are genuinely $0 in models.dev; zero cost with
  positive tokens is currently surfaced as `Unavailable`, which cannot
  distinguish "genuinely free" from "unknown pricing".

Burnly already has `CostKind::BurnlyCalculated` in the domain
(`domain/usage.rs`) and the storage mapping (`reconciliation/mapping.rs`
maps it to `burnly_calculated`). This proposal puts that kind to use.

## Recommendation

Add a **Burnly-owned cost calculator** that prices token usage from an
**embedded, build-time models.dev snapshot** (pinned, offline-first), and
wire it into the collector pipeline with a strict precedence chain that
never overrides a better source.

### Cost precedence chain (the 4 rules)

1. **Source-reported** — Command Code (`costUsd`), Cline: use as-is.
   `CostKind::SourceReported`.
2. **Collector-calculated** — ccusage sources (Claude, Codex, OpenCode, Pi):
   use as-is. `CostKind::CollectorCalculated`.
3. **Burnly-calculated** — Grok, Antigravity, ZCode (no cost reported):
   compute from tokens × embedded models.dev snapshot.
   `CostKind::BurnlyCalculated`.
4. **Gap-fill** — when a collector _reports_ cost but it is `0` with
   positive tokens (model missing from its pricing table), Burnly fills from
   the embedded snapshot. `CostKind::BurnlyCalculated`. This applies to
   Command Code, Cline, and ccusage sources when they produce
   zero-with-tokens.

### Pricing source

- **Primary**: a pinned, embedded snapshot of `https://models.dev/api.json`
  (per-M USD values converted to per-token at load, mirroring ccusage's
  models.dev handling).
- Regenerated by a `chore(pricing)` script + CI check, mirroring ccusage's
  snapshot flow.
- Free-tier models (`*-free`, explicit `$0`) remain `NotApplicable` with a
  note; unknown models stay `Unavailable`.

### Calculator shape

A pure domain function in the application layer:

```rust
fn calculate_cost(
    model: &str,
    tokens: &TokenUsage,
    pricing: &EmbeddedPricing,
) -> UsageCost
```

- Input/output/cache-read/cache-write buckets priced at per-token rates.
- Long-context tier (input > 200K) at `above_200k` rates when the snapshot
  provides them.
- Rounding to integer micros deterministic (round half-up), matching the
  existing cost conventions.
- No network, no config overrides, no shell.

## Architecture Impact

- New `application/cost/` module (or `domain/cost.rs`) owning the pure
  calculator + embedded snapshot parsing. Keep it framework-free per the
  domain rules.
- Collector mappers (grok, antigravity, zcode) gain access to the calculator
  via a shared port, so they emit `BurnlyCalculated` instead of
  `Unavailable`.
- The gap-fill rule is applied where candidates are produced (mapper or a
  post-map normalization step) so all four rules live in one place.
- `CostKind::BurnlyCalculated` storage path already exists; no migration.

## Open Questions

- Should the calculator live in `domain/` (pure, no IO) or `application/`
  (owning the snapshot)? Proposal: `application/cost/` with the snapshot as
  an application resource, calculator functions pure.
- Does gap-fill apply to free-tier `$0` models? Proposal: no — a model
  explicitly priced at $0 in the snapshot stays `NotApplicable`; gap-fill
  only fires when the _collector_ reports 0 because it lacks the model.
- Should ccusage sources receive gap-fill even though their cost comes from
  ccusage's own tables? Proposal: yes, only when ccusage reports
  zero-with-tokens (its table missed the model).

## Risks And Constraints

- Snapshot staleness: models.dev is community-maintained; pin + regenerate +
  review process required (same cadence concern as ccusage).
- Divergence: Burnly-calculated numbers may differ from ccusage's for the
  same model; acceptable because gap-fill only fires when ccusage cannot
  price it.
- Privacy: no new data read; calculator is pure token arithmetic.

## Out Of Scope

- Replacing ccusage's cost for sources it can price.
- Live pricing fetch at runtime (offline-first contract).
- Subscription-bill accuracy (estimate only).
