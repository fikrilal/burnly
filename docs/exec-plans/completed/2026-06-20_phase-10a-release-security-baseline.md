# 2026-06-20 Phase 10A Release Security Baseline

## Objective

Lock Burnly's production Tauri capability, CSP, native command, and dependency
boundaries to least privilege before release packaging expands.

## Acceptance Criteria

- Production capability files grant only reviewed commands to reviewed windows.
- CSP is explicit and compatible with Burnly's local-only runtime.
- Webview code has no broad shell, process, or filesystem access.
- Native plugins and permissions have documented product justification.
- Harness checks fail on accidental privilege expansion or insecure release
  configuration.

## Risk Class

`high`

## Impact Areas

- Tauri capabilities and configuration
- CSP and frontend asset policy
- Plugin inventory
- Architecture/security harness
- Release dependency review

## Design Review

- Complexity introduced: explicit production security policy and drift checks.
- Owning modules: Tauri config owns grants; `src/ipc/` owns frontend-native
  access; harness owns policy enforcement.
- Interface depth: React continues using Burnly IPC instead of native plugin
  APIs.
- Special cases: development tooling must not leak into production grants.
- New abstractions are unnecessary unless policy checks repeat.
- Existing architecture harness should absorb enforceable rules.

## Test Plan

- Behavior and invariants to prove: only reviewed IPC/native operations are
  reachable from the webview.
- Lowest stable test layer: configuration/harness tests and production build.
- Failure paths: broad glob, shell grant, unrestricted filesystem path, unsafe
  CSP directive, development-only capability in release.
- Fixtures or fakes: intentionally insecure configuration snippets for harness
  self-tests.
- Runtime or platform evidence: production build launches with enforced CSP.
- Relevant commands: `pnpm architecture:check`, `pnpm build`, `pnpm verify`.

## Decisions

- Do not grant direct shell or broad filesystem access to React.
- The main webview receives only registered Burnly commands and Tauri event
  listen/unlisten.
- Opener, dialog, notification, and single-instance plugins remain Rust-only.
- Inline styles remain allowed because the current UI stack emits style
  attributes; scripts cannot use dynamic evaluation.
- Application command permissions are generated by `AppManifest` and checked
  against the Rust IPC contract registry.
